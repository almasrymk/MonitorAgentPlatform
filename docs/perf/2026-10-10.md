# Release load test 2026-10-10 (M10, MC-1004)

Command (raw numbers in `2026-10-10-load.json`):

```
dotnet run --project tools/MonitorCloud.DeviceSimulator -c Release -- load --devices 1500 --duration 20m \
  --gateway http://localhost:5301 --report docs/perf/2026-10-10-load.json --server-process MonitorCloud.Api
```

## Setup

- **Machine:** the same development laptop as M5 runs everything: API (Release build, Development configuration,
  fake Licensing), SQL Server 2022, the simulator and the portal. Intel Core i7-1165G7 (4 cores / 8 threads),
  32 GB. It is weaker than the planned production host, and the load generator shares it with the server.
- **Data:** the demo seed (2,373 devices, 7 days of history) plus 1,500 simulated devices enrolled across the demo
  customers with free seats.
- **Rate limits** raised for the run with environment variables (one machine, one IP):
  `RateLimiting__Enroll__PermitLimit`, `RateLimiting__AgentToken__PermitLimit`, `RateLimiting__Auth__PermitLimit`,
  `Agent__EnrollPerFingerprintPerHour`.
- **Traffic per device:** one gRPC stream (connections spread over the first minute), a heartbeat every 30 s, one
  guaranteed `MetricBatch` and one snapshot per minute. **20 minutes**, twice the required 10, to confirm the memory
  trend left open in M5.
- **API probe** every 2 s during the whole run, as the Acme administrator and the platform administrator: the
  device list (24 items, and a filter that changes every round), the three dashboards (they are not cached), 7 days
  of device metrics, and a sign-in every 10 s.
- **Live probe:** a platform administrator connected to `/hubs/live` and subscribed to 50 of the simulated devices.
  It measures (a) Hello to `deviceStateChanged` Online, and (b) for 20 of them, at the end, closing the stream
  without a Goodbye to `deviceStateChanged` Offline.

### Lighthouse

Measured on the production build (`ng build`) behind a static server with Brotli compression and long cache
headers, as in production, on the signed-in Customer Dashboard (Lighthouse user flow; the session cannot be
created by a plain Lighthouse run). The portal is a desktop operations console: every design in `docs/design` is a
desktop layout. The desktop profile meets the target.

The mobile profile is limited by the chain of round trips before the first paint: the main script, then the
session restore (`/auth/refresh`), then the route chunk, then the dashboard data. Each round trip costs 150 ms or
more on simulated slow 4G. Server-side rendering or a pre-rendered shell would be needed to change that. This is
not planned (ADR 0010).

The run found one real problem, now fixed. The chart components imported the ECharts barrels `echarts/charts` and
`echarts/components`, which hold every chart type, as two lazy chunks of 262 kB each. They now import the five
parts used by name from one module (`echarts-setup`, 159 kB transferred), loaded when the first chart appears.
