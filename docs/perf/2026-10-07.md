# Load test 2026-10-07 (M5 acceptance)

Command (raw numbers in `2026-10-07-load.json`):

```
dotnet run --project tools/MonitorCloud.DeviceSimulator -c Release -- load --devices 1500 --duration 10m \
  --gateway http://localhost:5301 --report docs/perf/2026-10-07-load.json --server-process MonitorCloud.Api
```

## Setup

- **Machine:** one development laptop runs everything: the API (Release, Development configuration, fake
  Licensing), SQL Server 2022, the simulator and the portal dev server.
  - CPU: Intel Core i7-1165G7, 4 cores / 8 threads.
  - Memory: 32 GB.
  - This machine is weaker than the planned production host, and the load generator shares it with the server.
- **Data:** the demo seed (2,373 devices and 7 days of history) plus 1,500 simulated devices, enrolled across the
  demo customers that have free seats.
- **Rate limits:** raised through environment variables so 1,500 enrollments fit in one run. The production
  limits apply per IP address, and one simulator machine has a single IP.
  - `RateLimiting__Enroll__PermitLimit`
  - `RateLimiting__AgentToken__PermitLimit`
  - `Agent__EnrollPerFingerprintPerHour`
- **Traffic per device:**
  - One gRPC stream, with connections spread over the first minute.
  - A heartbeat every 30 s.
  - One guaranteed `MetricBatch` per minute.
  - One snapshot per minute.
- **API probe:** while the load ran, the Acme administrator called `GET /devices` (24 items) and `GET /dashboard`
  every 2 s.

The acknowledgement latency is mostly the writer's 2-second flush interval (`Telemetry:FlushSeconds`). The
database time per flush stayed far below that.
